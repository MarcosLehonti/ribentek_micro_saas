Cómo funciona el Módulo
de Suscripción Dinámica

Esta guía explica en lenguaje sencillo cada parte del sistema de suscripciones que vamos a construir para Odoo 17. Está pensada para que cualquier persona del equipo pueda entender el flujo completo: desde que el cliente compra hasta que se le bloquea el acceso si no renueva.

0
Modelos de datos — Los "cajones" del sistema
La base de datos: qué guardamos y por qué

Antes de entender el flujo, hay que entender dónde vive cada dato. En Odoo, los "modelos" son como las tablas de una base de datos: cada uno guarda un tipo específico de información. Vamos a necesitar 6 modelos principales.

🗂️ Plan de Suscripción — Define cuánto cuesta el servicio
Es el catálogo de precios. Aquí defines que un usuario cuesta, por ejemplo, 100 Bs al mes. Si en el futuro cambias el precio, solo cambias el plan. No afecta a los clientes que ya tienen suscripción activa porque sus facturas ya fueron generadas.
📄 Suscripción Principal — El "contrato" con el cliente
Es el registro central de cada cliente. Piénsalo como el contrato firmado: dice quién es el cliente, qué plan tiene, en qué instancia está y en qué estado se encuentra (activa, pausada, cancelada). Cada empresa cliente tiene exactamente una suscripción.
👤 Línea por Usuario ← La pieza más importante — Un registro por cada empleado
Este es el corazón del sistema. En lugar de decir "esta empresa tiene 5 usuarios hasta el mes 7", el sistema dice "este usuario específico está pagado desde el día X hasta el día Y". Esto permite que cada empleado tenga su propia fecha de vencimiento independiente, lo cual resuelve exactamente el problema de agregar usuarios a mitad del período.
💡 ¿Por qué una línea por usuario y no una por empresa?
Imagina que la empresa ABC tiene 5 empleados pagados por 7 meses y al mes 4 entra un empleado nuevo. Si usáramos un solo registro para toda la empresa, sería muy difícil saber cuándo vence el nuevo. Con una línea por usuario, el nuevo simplemente tiene su propia línea que dice "pagado desde hoy hasta dentro de 7 meses". Sin líos, sin prorrateos complicados.
🏗️ Instancia Odoo — El servidor donde corre el Odoo del cliente
Cada instancia es una instalación de Odoo con su propia base de datos y su propia URL (ej: empresa.tuapp.com). Una instancia puede alojar a varias empresas clientes al mismo tiempo para aprovechar mejor el servidor. Este modelo registra cuántos usuarios puede tener como máximo y cuántos tiene actualmente.
🧾 Factura — El cobro por el servicio
Es el modelo estándar de Odoo para facturas, pero le agregamos un campo que la vincula a la suscripción. Se genera una factura por cada evento de cobro: la compra inicial, agregar un usuario nuevo, renovar, etc. Esto da una trazabilidad completa de todos los pagos.
🛒 Orden de Venta — La solicitud de compra del cliente
Es el modelo estándar de Odoo para ventas, al que le agregamos tres campos clave: cuántos meses compra, cuántos usuarios, y el tipo de orden (nueva suscripción, agregar usuario, o renovación). Es el punto de partida de todo: sin orden de venta no hay factura, sin factura no hay suscripción.
📐 La fórmula de cobro
Total = Precio del plan × Cantidad de usuarios × Meses elegidos
Ejemplo: 100 Bs × 5 usuarios × 7 meses = 3,500 Bs — se cobra todo por adelantado en una sola factura.
1
Compra Inicial desde el Portal
Del primer clic del cliente hasta que su Odoo está listo

Este es el flujo que recorre un cliente nuevo: desde que entra a la tienda del portal hasta que tiene su Odoo funcionando. Son 7 pasos que mezclan acciones del cliente, del sistema y del administrador.

  1. El cliente entra a la tienda del portal Ve un único producto llamado "Suscripción Odoo". Solo puede agregar uno al carrito (el sistema lo valida). No hay opciones confusas de mensual/semestral/anual: eso se elige en el siguiente paso.
  2. Configura su suscripción con el widget dinámico En la ficha del producto aparece un configurador interactivo: un selector de meses (de 1 a 36) y un campo para escribir cuántos usuarios necesita. El precio total se actualiza automáticamente en tiempo real. Ej: mueve el selector a 7 meses, escribe 5 usuarios → se muestra "Total: 3,500 Bs".
  3. Agrega al carrito y paga El sistema guarda en la orden de venta los meses y usuarios elegidos (no solo el precio). El cliente paga por transferencia, QR u otro método disponible.
  4. La orden llega al Odoo Maestro El administrador recibe la orden de venta en su panel. Puede ver el cliente, los meses comprados y la cantidad de usuarios. La orden llega en estado "borrador".
  5. El admin verifica el pago Una vez que confirma que el dinero llegó (revisando el banco, el QR escaneado, etc.), confirma la orden. Esto es manual por ahora, pero podría automatizarse con una pasarela de pago.
  6. Se genera la factura automáticamente Al confirmar la orden, el sistema crea la factura y la marca como pagada. La factura dice exactamente: N usuarios × X meses × 100 Bs = Total.
  7. Se crean la suscripción y las líneas por usuario Cuando la factura queda como pagada, se dispara una acción automática que crea la suscripción principal y una línea de suscripción por cada usuario comprado, con fecha de inicio hoy y fecha de fin en X meses.
⚙️ ¿Qué es la "acción automática"?
En Odoo existe la posibilidad de configurar reglas que digan "cuando pase X, hacer Y automáticamente". En este caso, la regla dice: cuando una factura vinculada a una suscripción cambie a estado pagada → crear suscripción + líneas de usuario. No hace falta que el admin haga nada manualmente.
Ejemplo: Empresa Boticas del Sur
El dueño entra al portal, elige 7 meses y 5 usuarios. Ve que el total es 3,500 Bs. Paga por QR. El admin recibe la orden, confirma que llegó el pago y la aprueba. En ese momento, el sistema crea automáticamente la suscripción de Boticas del Sur con 5 líneas de usuario, cada una con fecha inicio hoy y fecha fin en 7 meses.
2
Asignación de Instancias (micro_SaaS)
Dónde y cómo se aloja el Odoo del cliente

Una vez creada la suscripción, el módulo micro_SaaS se encarga de preparar el Odoo donde el cliente va a trabajar. Aquí hay una decisión importante: ¿crear una instalación nueva o agregar al cliente a una instalación que ya existe?

Una instancia es básicamente un Odoo instalado con su propia base de datos. La idea es que varias empresas clientes puedan compartir la misma instancia para aprovechar mejor los recursos del servidor, siempre y cuando no se exceda el límite de usuarios configurado.

🏗️ ¿Cuándo se crea una instancia nueva?
Se crea una instancia nueva cuando: (1) el cliente es el primero o (2) todas las instancias existentes ya llegaron a su límite de usuarios. En los demás casos, se agrega la empresa cliente a una instancia que tenga espacio disponible.
  1. El sistema busca una instancia con cupo disponible Al activarse la suscripción, el módulo revisa si existe alguna instancia donde la suma de usuarios activos sea menor al máximo permitido. Si encuentra una, asigna el nuevo cliente ahí.
  2. Si no hay cupo: crear instancia nueva micro_SaaS crea una nueva base de datos PostgreSQL, configura el subdominio (ej: boticasdelsur.tuapp.com), instala los módulos base de Odoo y crea el usuario administrador del cliente.
  3. Se vincula la suscripción con la instancia El campo "instancia" de la suscripción se llena con la instancia asignada. Así el sistema siempre sabe en qué servidor está cada cliente.
  4. Se notifica al cliente por email El cliente recibe un correo con su URL de acceso, usuario, contraseña temporal, fecha de vencimiento y el número de usuarios que puede crear.
⚠️ Regla de negocio crítica: La instancia siempre debe tener como límite máximo la suma de líneas de suscripción activas de todas las empresas que aloja. Si en una instancia hay 2 empresas con 5 usuarios cada una, el límite máximo es 10 usuarios totales. Intentar crear el usuario 11 debe ser bloqueado.
3
Gestión de Usuarios en Período Activo
Qué pasa cuando un empleado se va o llega uno nuevo

Una vez que la suscripción está activa, el día a día consiste en que el administrador del cliente va agregando o quitando empleados de su Odoo. El sistema necesita reaccionar de forma diferente según lo que pase.

✅ Estado normal
Todos los usuarios tienen una línea de suscripción activa y vigente. El acceso a la instancia funciona normalmente. No hay ninguna acción requerida hasta que alguien se vaya o llegue alguien nuevo.
➖ Cuando un empleado se va
El administrador desactiva al usuario en su Odoo (res.users.active = False). Esto bloquea el acceso de esa persona inmediatamente. Sin embargo, la línea de suscripción sigue activa hasta su fecha de vencimiento original. ¿Por qué? Porque ese período ya fue pagado por adelantado y no hay reembolso. El "cupo" librado se podría usar para un nuevo empleado — pero solo si ese nuevo empleado también paga su período.
➕ Cuando llega un empleado nuevo
El administrador intenta crear un usuario nuevo en su Odoo. El sistema detecta que no existe una línea de suscripción activa para ese usuario y bloquea la creación hasta que se pague el addon correspondiente. También envía una notificación automática al administrador explicando qué debe hacer.

🔑 La regla más importante de esta sección
El sistema no rebaja el precio porque un empleado se fue. El precio pagado es fijo para el período comprado. Lo que sí puede hacer el cliente es: cuando llegue el momento de renovar, renovar solo con los empleados activos y no pagar por el que ya no está.
4
Agregar un Nuevo Usuario (Addon)
El flujo completo cuando entra un empleado nuevo a mitad del período

Este es probablemente el flujo más frecuente después de la compra inicial. Alguien del equipo deja la empresa o el negocio crece y hay que incorporar un nuevo empleado que ya quiere trabajar en el Odoo del cliente.

Lo llamamos "addon" (o complemento) porque no es una suscripción nueva, sino un usuario adicional que se agrega a una suscripción ya existente.

  1. El admin crea el usuario en su Odoo El administrador del cliente intenta crear un nuevo usuario en su instancia. El sistema detecta que no hay una línea de suscripción activa para ese usuario.
  2. El sistema genera una alerta automática Se envía un correo al admin del cliente (y al admin del sistema maestro) diciendo que se detectó un usuario sin suscripción, con el nombre del usuario y un enlace directo para pagar el addon.
  3. El admin va al portal y configura el addon En la sección "Mi Suscripción" del portal, el admin ve el usuario pendiente y puede elegir cuántos meses quiere pagar para ese empleado. El precio se calcula automáticamente.
  4. Paga y el sistema activa al usuario Se genera una orden de venta tipo "addon", se crea la factura, el admin paga, y al confirmarse el pago se crea la línea de suscripción para ese usuario. El usuario queda habilitado en la instancia.
Ejemplo detallado — Empresa ABC · Día 15 del Mes 4
El equipo tiene 5 empleados pagados por 7 meses desde el mes 1. El jefe contrata a María García. El jefe la agrega a su Odoo → el sistema bloquea el acceso y avisa. El jefe va al portal y elige 7 meses para María → el sistema calcula 700 Bs (1 usuario × 7 meses × 100 Bs). El jefe paga. El sistema crea una nueva línea para María: inicio día 15 del mes 4, vencimiento día 15 del mes 11. El resto del equipo vence al final del mes 7. Las fechas son independientes.
💡 Opción "Sincronizar con el equipo"
Para clientes que prefieren que todos sus empleados venzan el mismo día, se puede ofrecer en el portal una opción de "sincronizar". Si el equipo vence en 3.5 meses, el sistema redondea hacia arriba y cobra 4 meses para el nuevo usuario. Así todos quedan con la misma fecha de vencimiento y la renovación es más sencilla.
⚠️ ¿Qué pasa si el usuario nuevo intenta trabajar antes de pagar? No puede. El sistema solo habilita el acceso (res.users.active = True) cuando la factura del addon queda marcada como pagada. Mientras no haya pago, el usuario existe en el sistema pero no puede iniciar sesión.
5
Control de Vencimiento y Suspensión
Qué hace el sistema cada día para gestionar los plazos

Todos los días a medianoche, el sistema ejecuta un proceso automático llamado "proceso diario". Este proceso revisa todas las líneas de suscripción y toma decisiones según las fechas de vencimiento.

El objetivo es que los clientes siempre sepan con antelación cuándo vencen, para que puedan renovar sin perder acceso. Y si no renuevan, el sistema debe bloquear el acceso de forma ordenada y segura.

📢 Sistema de avisos escalonados
El sistema envía 4 correos de aviso antes del vencimiento. Cada uno tiene un tono más urgente:
  • 30 días antes: correo informativo tranquilo — "Tu suscripción vence en un mes"
  • 15 días antes: correo con más urgencia — "Renueva pronto para no perder acceso"
  • 7 días antes: correo urgente + banner visible en el portal del cliente
  • 1 día antes: correo de última llamada + notificación al administrador del sistema
Todos los correos incluyen un botón directo de renovación.

Cuando llega la fecha de vencimiento, el proceso diario actúa de la siguiente manera según cuántos usuarios hayan vencido:

🟡 Suspensión parcial — Solo algunos usuarios vencieron
Solo se bloquean los usuarios cuya línea de suscripción venció. Los demás siguen trabajando normalmente. El estado de la suscripción pasa a "parcialmente activa". El admin recibe un aviso con los usuarios bloqueados y la opción de renovarlos.
🔴 Suspensión total — Todos los usuarios vencieron
Se bloquea el acceso de todos los usuarios de esa empresa. La suscripción pasa a estado "pausada". La instancia sigue funcionando (los datos están seguros) pero nadie puede entrar. Empieza el período de gracia de 30 días.
  1. Período de gracia: 30 días para renovar Durante 30 días después del vencimiento total, el cliente puede renovar y recuperar el acceso inmediatamente. Los datos no se tocan durante este tiempo.
  2. Último aviso antes de cancelar Si pasan 30 días sin renovar, el sistema envía un último correo explicando que los datos se eliminarán pronto y ofreciendo descargar un backup.
  3. Cancelación de la suscripción El administrador del sistema puede optar por archivar la instancia o dar más tiempo. Si no hay respuesta, la instancia se detiene y la suscripción pasa a "cancelada".
  4. Retención de datos por 90 días adicionales Los datos del cliente se guardan en backup por 90 días más después de la cancelación, por si el cliente decide reactivar o necesita recuperar información.
⚠️ Nunca eliminar datos sin backup previo y sin haber notificado al cliente con suficiente antelación. Esta es una regla de negocio no negociable para proteger la confianza del cliente y evitar problemas legales.
6
Flujo de Renovación
Cómo el cliente extiende su suscripción

Renovar es muy parecido a comprar por primera vez, con una diferencia clave: el sistema ya sabe quiénes son los usuarios y puede calcular inteligentemente las nuevas fechas de vencimiento.

El cliente puede renovar desde el portal en cualquier momento: antes de que venza (para no perder continuidad), justo al vencer, o incluso después de haber sido bloqueado (mientras esté en período de gracia).

  1. El admin entra al portal y va a "Mi Suscripción" Allí puede ver todos sus usuarios, cuáles están activos, cuáles vencieron, y las fechas exactas de cada uno. Hay un botón de "Renovar" visible y accesible.
  2. Elige qué renovar y por cuántos meses Puede renovar todos los usuarios a la vez o seleccionar solo algunos. Por ejemplo, si salió un empleado, puede renovar solo los 4 restantes y no pagar por el que ya no está. Elige cuántos meses quiere pagar.
  3. El sistema calcula las nuevas fechas automáticamente Si renueva antes de vencer, la nueva fecha de inicio es la fecha de fin actual (sin perder días). Si renueva después de vencer, la nueva fecha de inicio es el día del pago.
  4. Paga y el sistema reactiva el acceso Se genera una orden de tipo "renovación" y su factura correspondiente. Al pagar, las líneas de suscripción se actualizan, los usuarios se reactivan y el cliente recibe un correo de confirmación.

7
Los Estados de la Suscripción
Cómo saber en qué momento está cada cliente

Cada suscripción tiene un estado que indica en qué punto del ciclo de vida se encuentra. Esto es lo que el administrador ve en el panel de Odoo Maestro y lo que controla qué puede hacer el cliente.

borrador
La orden de venta fue creada pero todavía no se ha confirmado el pago. El cliente puede haber llenado el formulario pero aún no pagó. El acceso a la instancia no está disponible todavía.
pago_pendiente
La orden fue confirmada y se generó la factura, pero el pago no ha sido registrado aún en el sistema. El admin está esperando que el dinero llegue o que se confirme la transacción.
activa
Todo en orden. Todos los usuarios tienen líneas vigentes y pueden acceder normalmente a su instancia Odoo. Este es el estado "feliz" del sistema.
parcialmente_activa
Algunos usuarios tienen líneas vencidas y están bloqueados, pero otros siguen activos. El acceso a la instancia funciona para los usuarios vigentes. El admin debe renovar o retirar a los usuarios bloqueados.
pausada
Todos los usuarios están bloqueados. Nadie puede entrar a la instancia. Los datos están seguros y la instancia sigue corriendo. El cliente tiene 30 días para renovar antes de que se inicie el proceso de cancelación.
cancelada
La suscripción terminó definitivamente. La instancia fue detenida o archivada. Los datos se guardan en backup por 90 días adicionales por política de retención, luego se eliminan permanentemente.
🔄 ¿Puede una suscripción volver de "cancelada" a "activa"?
Sí, pero requiere intervención manual del administrador. Si el cliente quiere reactivar después de una cancelación, el admin puede restaurar el backup y crear una nueva suscripción desde cero. No es automático porque implica trabajo técnico de restauración.
8
Módulos a Desarrollar
Qué hay que programar y en qué orden hacerlo

Todo lo que describe esta guía se implementa en tres módulos de Odoo. Uno ya existe (micro_SaaS) y solo necesita ampliarse. Los otros dos son nuevos y se construyen desde cero.

El orden recomendado de desarrollo es de abajo hacia arriba: primero la base de datos y la lógica, luego el portal y finalmente la integración con micro_SaaS.

📦 subscription_dynamic Módulo nuevo · Desarrollar primero
¿Qué hace? Es el núcleo de todo el sistema. Define los modelos de datos (plan, suscripción, línea), contiene toda la lógica de negocio y controla los estados.

Incluye: los 6 modelos de datos descritos en la sección 0, el proceso diario automático que revisa vencimientos, las reglas de automatización (cuando factura = pagada → crear suscripción), las 4 plantillas de correo para los avisos de vencimiento, y las acciones sobre res.users (bloquear / desbloquear acceso).

Depende de: sale, account, mail (módulos estándar de Odoo).
🌐 subscription_portal Módulo nuevo · Desarrollar segundo
¿Qué hace? Agrega toda la experiencia del cliente en el portal web: el configurador de compra, el panel de gestión y los flujos de addon y renovación.

Incluye: el widget de JavaScript con el selector de meses y usuarios (con cálculo en tiempo real), la página "Mi Suscripción" donde el cliente ve todos sus usuarios y fechas, el flujo de compra de addon para nuevos empleados, el flujo de renovación con selección de usuarios, y el historial completo de facturas.

Depende de: subscription_dynamic, website_sale (módulos de Odoo).
🔧 micro_saas (ampliar el existente) Módulo existente · Ampliar tercero
¿Qué cambia? El módulo que ya tienes necesita conocer el concepto de suscripción para poder controlar el acceso de los usuarios según si están pagados o no.

Se agrega: el campo "empresas cliente" (para que una instancia pueda tener N empresas), el método para verificar si hay cupo antes de habilitar un usuario, el hook que se activa cuando una suscripción se activa (para habilitar o deshabilitar usuarios automáticamente), y la relación con la suscripción para saber cuántos usuarios está pagando cada empresa en esa instancia.

Importante: al ser una ampliación del módulo existente, hay que tener cuidado de no romper el comportamiento actual. Se recomienda usar herencia de modelos de Odoo.
📋 Reglas de negocio que nunca deben olvidarse al programar
  • Un usuario solo puede tener una línea activa por suscripción para evitar cobros dobles
  • Al desactivar un usuario, su línea no se elimina — se guarda el registro porque ya fue cobrado
  • Todo SO de addon debe referenciar la suscripción padre para mantener trazabilidad completa
  • La instancia solo puede tener usuarios que sean menor o igual a la suma de líneas activas
  • Siempre debe existir un período de gracia de 30 días antes de bloquear la instancia
  • Nunca eliminar datos sin backup previo y sin notificar al cliente con tiempo suficiente
